# Running ipwatch with a systemd user timer

This guide covers the systemd scheduling option in detail: what the generated units contain, how they behave across login, logout, boot and suspend, and how to control and customise them. For the short version, see [SETUP.md section 4a](../SETUP.md#4a-systemd-user-timer-recommended-where-cron-is-not-installed-such-as-fedora-workstation).

A systemd user timer is an alternative to cron. It needs no root access and no extra packages on distributions that run systemd, which makes it the natural choice where cron is not installed, such as Fedora Workstation. Use the timer **or** cron, not both.

## How it works

Two unit files work together:

| Unit | Role |
| --- | --- |
| `ipwatch.timer` | Starts `ipwatch.service` at second 0 of every minute |
| `ipwatch.service` | Runs `ipwatch run --config <your config.yaml>` once and exits (`Type=oneshot`) |

The timer does **not** decide when a sample is taken. Each minute it starts the service, and the tool itself checks `interval_minutes` from your YAML, exactly as it does under cron:

1. The timer fires at `hh:mm:00`.
2. The service starts `ipwatch run`, which takes the lock and reads `state.json`.
3. If less than `interval_minutes × 60 − 30` seconds have passed since the last attempt, the tool exits immediately with code 0. No network request is made and nothing is written. This is what happens on most minutes.
4. Otherwise it takes a sample: discovers the IP, enriches it with GeoIP, appends a record to the JSON Lines log, updates state, and sends any change email.
5. The service exits and goes back to inactive until the next minute.

Running every minute and letting the tool decide keeps one simple schedule for any interval. You change `interval_minutes` in the YAML without touching the units, and the 30-second grace keeps a 5-minute interval at 5 minutes.

### The generated units

Generated by `ipwatch systemd-units`, with your real paths in place of these placeholders:

```ini
# ipwatch.service
[Unit]
Description=ipwatch external IP observation (/home/YOUR_USER/external-ip-monitor/config.yaml)
Documentation=https://github.com/PurpleSentinel/external-ip-monitor

[Service]
Type=oneshot
ExecStart=/home/YOUR_USER/external-ip-monitor/.venv/bin/python -m ipwatch run --config /home/YOUR_USER/external-ip-monitor/config.yaml
# 1: IP discovery failed (an error record was written). 3: change email queued for retry.
SuccessExitStatus=1 3
# The tool bounds its own requests; this only stops a run that is stuck regardless.
TimeoutStartSec=30min
NoNewPrivileges=yes
```

```ini
# ipwatch.timer
[Unit]
Description=Run ipwatch.service every minute; interval_minutes in the YAML decides when a sample is due

[Timer]
OnCalendar=*-*-* *:*:00
# Fire on the minute, like cron. The default AccuracySec=1min would spread runs across
# the minute, which the tool's 30-second due-time grace does not absorb.
AccuracySec=1s

[Install]
WantedBy=timers.target
```

| Setting | Why |
| --- | --- |
| `OnCalendar=*-*-* *:*:00` | Every minute, on the minute, matching cron's `* * * * *` |
| `AccuracySec=1s` | systemd normally coalesces timers within a 1-minute window to save power. Without this, run times would wander within the minute, and a 5-minute interval could slip to 6 |
| `Type=oneshot` | The service is a short-lived command, not a daemon |
| `SuccessExitStatus=1 3` | Exit 1 (no IP discovered; an error record was written) and exit 3 (change email failed and is queued for retry) are expected outcomes. They are logged to the journal but do not mark the unit as failed |
| `TimeoutStartSec=30min` | Backstop only. Each request already has its own timeouts |
| `NoNewPrivileges=yes` | The process and its children (curl) can never gain privileges, for example through setuid binaries |
| `ExecStart` with absolute paths | The interpreter is the virtualenv that generated the units, so the right Python and packages are used without relying on `PATH` |
| No `Persistent=` (default `no`) | Missed minutes are not replayed. The tool's own interval check already takes one sample at the first run after a gap; see below |
| No `WakeSystem=` (default `no`) | The timer never wakes a sleeping laptop |

If the timer fires while a previous run is still in progress, for example a slow network request, systemd does not start a second copy; the tool's lock would also prevent overlap.

## Installing the units

From the repository directory, using the virtualenv you installed ipwatch into:

```bash
.venv/bin/ipwatch systemd-units --config "$PWD/config.yaml"           # review: prints both units
.venv/bin/ipwatch systemd-units --config "$PWD/config.yaml" --write   # install
systemctl --user daemon-reload
systemctl --user enable --now ipwatch.timer
```

`--write` places the files in `~/.config/systemd/user/`, or in `$XDG_CONFIG_HOME/systemd/user/` if that variable is set. It never enables or starts anything. Rerunning it is safe:

- Files that already match are reported as `unchanged`.
- Files that differ, for example because you edited them by hand, are left alone and the command fails with exit code 2, unless you add `--overwrite`.

`enable --now` does two things. *enable* links the timer into `timers.target`, so it starts whenever your user manager starts. *--now* also starts it immediately. Only the timer is enabled; the service is started by the timer and is never enabled itself.

Paths containing spaces, quotes, `%` or `$` are quoted and escaped for systemd automatically. Paths with control characters are rejected.

## Login, logout, boot and suspend

User timers run inside your **user manager**, a per-user instance of systemd (`systemd --user`). Whether sampling happens depends on whether that manager is running.

### Default behaviour (lingering off)

| Event | User manager | Sampling |
| --- | --- | --- |
| Boot, before anyone logs in | Not running | None |
| You log in (desktop, TTY or SSH) | Starts | Timer starts; the first run samples if an interval has elapsed |
| Screen locked | Running (the session still exists) | Continues |
| Another session opens or closes while one remains | Running | Continues |
| Last session ends (logout) | Stops after a short delay (logind's `UserStopDelaySec`, 10 s by default) | Stops |
| Shutdown | Stops | Stops |

So by default ipwatch samples **only while you are logged in**. Closing the laptop lid usually suspends it (below), which is different from logging out.

### Lingering: sample from boot and after logout

Enable lingering for your user once:

```bash
loginctl enable-linger "$USER"
loginctl show-user "$USER" -p Linger     # Linger=yes
```

With lingering on, your user manager starts at **boot**, before any login, and keeps running after you **log out**, so the timer runs continuously while the machine is on. The setting persists across reboots. On Fedora's default policy, users can enable lingering for themselves without a password; other systems may ask for authentication.

| Event | User manager with lingering | Sampling |
| --- | --- | --- |
| Boot | Starts during boot | Starts without a login |
| Login / logout | Unaffected | Continues |
| Shutdown | Stops | Stops |

Things to know with lingering on:

- **Network at boot:** the first runs after boot can happen before Wi-Fi or other networking is up. That sample records `status: error` (exit 1, still a successful unit run) and reserves the interval, so the next attempt comes after `interval_minutes`. With a short interval this costs little; nothing else needs configuring.
- **Email password from the environment:** with `email.password_env`, the variable must exist in the user manager's environment, not just in your shell, especially at boot. `email.password_file` avoids this and is recommended.
- **Turning it off:** `loginctl disable-linger "$USER"`. Sampling then only happens while you are logged in again.

Lingering keeps all of your user services running after logout, not just ipwatch.

### Suspend and hibernate

While the machine sleeps nothing runs, and the timer does not wake it. After resume, the timer fires again within about a minute. Because the tool checks the time since the last attempt, the first run after resume takes a sample if one is due. There is exactly one catch-up sample; missed samples are never backfilled.

The same applies after any gap: logged out without lingering, powered off, or timer stopped. The first run afterwards samples straight away, and the regular interval resumes from there.

## Everyday control

All commands use `--user` and are run as you, without `sudo`.

| Task | Command |
| --- | --- |
| Show next and last trigger time | `systemctl --user list-timers ipwatch.timer` |
| Show the last run and its exit code | `systemctl --user status ipwatch.service` |
| Pause sampling until next login or boot | `systemctl --user stop ipwatch.timer` |
| Resume after a pause | `systemctl --user start ipwatch.timer` |
| Stop permanently (survives reboot and login) | `systemctl --user disable --now ipwatch.timer` |
| Re-enable | `systemctl --user enable --now ipwatch.timer` |
| Trigger a run now (still respects the interval) | `systemctl --user start ipwatch.service` |
| Take a sample now, regardless of the interval | `.venv/bin/ipwatch run --config "$PWD/config.yaml" --force --stdout` |
| Check whether the timer is enabled / running | `systemctl --user is-enabled ipwatch.timer` / `systemctl --user is-active ipwatch.timer` |

Notes:

- **`stop` versus `disable`:** stopping the timer pauses it, but because it is still enabled it starts again when your user manager next starts, at your next login or at boot with lingering. Use `disable --now` to stop it for good.
- **Manual runs alongside the timer** are safe. A forced run and a timer run share the same lock, so they cannot overlap, and a forced run reserves the next interval.
- **Changes to `config.yaml` need no restart.** Each run reads the YAML afresh.

## Configuration

### What lives where

| Setting | Where to change it | Needs |
| --- | --- | --- |
| Sampling interval, endpoints, GeoIP, email, output paths | `config.yaml` | Nothing; picked up at the next run |
| Config file location, repository location, virtualenv or Python version | The unit files | Regenerate: `systemd-units --write --overwrite`, then `daemon-reload` |
| Extra systemd options (priority, environment, schedule) | A drop-in override | `daemon-reload` (done for you by `systemctl --user edit`) |

### Regenerating after moving things

The units contain absolute paths. After moving the repository, the YAML file or the virtualenv, or rebuilding the virtualenv with a different Python, regenerate from the new location:

```bash
.venv/bin/ipwatch systemd-units --config "$PWD/config.yaml" --write --overwrite
systemctl --user daemon-reload
```

The timer does not need to be re-enabled. Running `systemd-units` without `--write` first shows what would change.

### Customising with drop-ins

To change systemd settings, use a **drop-in override** rather than editing the generated files. Drop-ins live in `~/.config/systemd/user/ipwatch.service.d/` or `ipwatch.timer.d/`, survive `--write --overwrite`, and keep your changes separate:

```bash
systemctl --user edit ipwatch.service     # opens an editor for an override file
systemctl --user cat ipwatch.service      # shows the unit plus all overrides
systemctl --user revert ipwatch.service   # removes all overrides
```

Examples:

```ini
# systemctl --user edit ipwatch.service: run at lower CPU and I/O priority
[Service]
Nice=10
IOSchedulingClass=idle
```

```ini
# systemctl --user edit ipwatch.service: supply email.password_env from a private file
[Service]
EnvironmentFile=%h/.config/ipwatch/smtp.env
```

Here `%h` is systemd's specifier for your home directory. The file should be mode 0600 and contain a line such as `SMTP_PASSWORD=...`. Avoid `Environment=SMTP_PASSWORD=...` directly in an override: `systemctl --user show` displays such values. `email.password_file` remains the simplest option.

**Changing the schedule** is possible but rarely useful, because `interval_minutes` already controls the sampling rate. If you do override `OnCalendar=`, keep `AccuracySec=1s`. Clear the old value first, because `OnCalendar` accumulates:

```ini
# systemctl --user edit ipwatch.timer: example only, every 2 minutes
[Timer]
OnCalendar=
OnCalendar=*-*-* *:00/2:00
```

A slower timer than `interval_minutes` delays samples to the next timer run.

### Development checkouts

The units run whatever ipwatch code the virtualenv contains. With an editable install (`pip install -e .`), that is the repository's **currently checked-out branch**: switching to a work-in-progress branch changes what the timer runs at the next minute. For unattended use, install normally (`pip install .`) and reinstall after updating.

## Logs and exit codes

ipwatch writes two kinds of output:

- **Observations** go to the JSON Lines log (`output.log_file`, by default `var/history.jsonl`). That is the record of IPs, countries and changes; see [LOG_FORMAT.md](LOG_FORMAT.md).
- **Diagnostics** go to stderr, which systemd sends to the journal: configuration problems, email delivery failures and refused recipients. Normal runs print nothing.

```bash
journalctl --user -u ipwatch.service -n 50            # recent entries
journalctl --user -u ipwatch.service -f               # follow live
journalctl --user -u ipwatch.service --since today    # today only
```

The journal also contains systemd's own "Starting… / Finished…" lines for every run, including the minutes when no sample was due.

| Exit code | Meaning | Unit result |
| --- | --- | --- |
| 0 | Sample recorded, not due yet, or another run holds the lock | success |
| 1 | IP discovery failed; an error record was appended | success (`SuccessExitStatus`) |
| 2 | Configuration or storage error; nothing recorded | **failed**; see the journal |
| 3 | Sample recorded, but the change email failed and is queued for retry | success (`SuccessExitStatus`) |

A failed unit does not stop the timer: it keeps trying every minute, so the problem is reported again until you fix it. List failed user units with `systemctl --user --failed`.

## Multiple configurations

To monitor IPv4 and IPv6 separately, give each configuration its own YAML file, its own output paths (see [SETUP.md section 6](../SETUP.md#6-ipv6-or-two-address-families)) and its own unit names:

```bash
.venv/bin/ipwatch systemd-units --config "$PWD/ipv6.yaml" --name ipwatch-ipv6 --write
systemctl --user daemon-reload
systemctl --user enable --now ipwatch-ipv6.timer
```

`--name` accepts letters, digits, `_`, `.` and `-`, and must start with a letter or digit. Every command in this guide works with the other name, for example `journalctl --user -u ipwatch-ipv6.service`.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| `list-timers` does not show ipwatch | Run `systemctl --user daemon-reload` and `enable --now`. Confirm the files are in `~/.config/systemd/user/` |
| Sampling stops when you log out | Lingering is off; see [Lingering](#lingering-sample-from-boot-and-after-logout) |
| Nothing recorded after boot until you log in | Lingering is off; this is expected |
| `ipwatch.service` shows `failed` | Exit code 2. Read `journalctl --user -u ipwatch.service`; usually the YAML, the password file permissions, or the state file |
| Timer runs but no new log lines | Usually not due yet (`interval_minutes`). Check the timestamp of the last record |
| `status=203/EXEC` or "No such file" | The units point at a moved or deleted virtualenv or config. Regenerate with `--write --overwrite` |
| `systemd-units --write` fails with "--overwrite" | The unit files differ from what would be generated, often after a hand edit. Review with `systemd-units` (no `--write`), then use `--overwrite`, and put customisations in drop-ins |
| Samples about a minute late | An override removed `AccuracySec=1s`, or the machine was suspended. Check with `systemctl --user cat ipwatch.timer` |
| Email failures | `journalctl --user -u ipwatch.service` shows the reason; `ipwatch test-email` checks the setup. Queued notices retry at the next due sample |
| `Failed to connect to bus` when running `systemctl --user` over SSH or `su` | Use a real login session for that user (SSH as the user, not `su`), or enable lingering |

## Removing the units

```bash
systemctl --user disable --now ipwatch.timer
rm ~/.config/systemd/user/ipwatch.service ~/.config/systemd/user/ipwatch.timer
rm -r ~/.config/systemd/user/ipwatch.service.d ~/.config/systemd/user/ipwatch.timer.d 2>/dev/null
systemctl --user daemon-reload
```

This removes only the scheduling. Your configuration, log, state and password file are untouched. If you enabled lingering only for ipwatch, turn it off with `loginctl disable-linger "$USER"`.
